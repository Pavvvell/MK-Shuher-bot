# Performance update — 2026-10-31

Current model: `gpt-6.1-sol` via Responses API. This supersedes the older Astra model setup described in README. Standard text rates: $2 per million input tokens and $10 per million output tokens; verify current pricing at https://developers.openai.com/api/docs/models/gpt-6.1-sol . Reasoning remains low for JSON and medium for ordinary answers and image analysis.

Run `sh switch-model.sh` to update the existing private deployment environment. It changes only OPENAI_MODEL, keeps a private backup, and deploys the application. Never commit the environment file.

Sheets titles and data ranges are reused only within one serialized request. Each write invalidates cached data for that tab, even if the write times out. Creating a tab invalidates all cached data for that workbook. Every new request starts fresh; current and historical workbooks have distinct keys. This does not provide database transactions or change the existing concurrency policy.

Validation: 121 offline unit tests and 95 simulated handler scenarios. The simulated worker chat uses 9 Sheets API calls instead of 25; photo invoice intake uses 9 instead of 23. These are request counts, not end-to-end latency measurements. No business records or employee messages are generated by these tests.

## Per-user queues — 2026-11-01

Different users can wait for OpenAI and Telegram concurrently; messages and callbacks from the same user run in arrival order. In-flight duplicate update IDs have their own lock and are checked against the persisted processed-update register before execution. Idle lock entries are removed.

Cloud Run concurrency and Telegram webhook max_connections are 4. Keep max instances at 1 and Uvicorn workers at 1: this is a single-process design, not a distributed queue. Sheets remains the persistent store; unacknowledged Telegram updates are retried on failure/restart. External message delivery is not guaranteed exactly once across crashes.

All Sheets calls use one dedicated worker thread. Complete stock check-and-write and linked procurement operations stay serialized; model and Telegram waits do not occupy that worker. Cache generations invalidate data in other active requests after bot writes. Permissions are rechecked in the same worker operation as confirmed writes. Manual edits made outside the bot are refreshed on the next request, as before. Task notification scans have a separate lock; PDF conversion has its own bounded worker.

Validation: 135 unit tests, including same-user ordering, cross-user progress, duplicate updates, cancellation, permission revocation, stock overspending and project decision conflicts. Replayed 95 synthetic handler scenarios with unchanged Telegram delivery counts. The queue benchmark uses a simulated one-second handler wait, not real model or network latency.
