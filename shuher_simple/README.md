# Шухер: модель та інструменти

Модель — `gpt-6.1-sol`, Responses API, `reasoning.effort=low`. Кожне звичайне
повідомлення спершу отримує модель. Вона відповідає або викликає типізовані
інструменти. Результат виконання повертається моделі. Окремих класифікаторів
намірів, регулярних виразів для маршрутизації й сценаріїв відповіді немає.

## Межі відповідальності

- `agent.py`: один модельний цикл, до 12 кроків, передача всіх Responses output
  items у наступний виклик, включно з reasoning items.
- `agent_schema.py`: опис доступних функцій і строгі JSON-схеми.
- `agent_tools.py`: читання, формування чернеток, файли, сповіщення; перевірка
  схем, прав, конкретних ID та фактичного результату виконання.
- `app.py`: Telegram transport, авторизація, черги, callback-кнопки та
  бізнес-сервіси. Визначати значення звичайного тексту цей шар не повинен.
- `store.py`, `business.py`, `projects.py`, `invoice_updates.py`: облік та
  перевірки. Заявка має проєкт/найменування/кількість/одиницю, отримує пов'язану
  закупівлю; склад не допускає видачі понад залишок; статуси мають допустимі
  значення; підтверджена зміна звіряється з попереднім значенням.

Персональна пам'ять у `_Shuher_Dialog` містить репліки і структуровані результати
інструментів, зокрема конкретні ID виданих рахунків. Фото зберігаються як Telegram
file ID, не як байти у Sheets. Пам'ять обмежена: старі повні ходи розмови
відкидаються; якщо необхідного переліку більше немає, модель повинна уточнити
або перечитати дані. Старі текстові діалоги переносяться без надання їм статусу
підтверджених результатів інструментів.

## Підтвердження й доступ

Нові рахунки та замовлення подаються інструментом `offer_invoice_projects`:
кожен оригінальний файл показується з кнопками затверджених проєктів.
Натискання автором кнопки проєкту одразу записує документ і надсилає власнику,
без другого підтвердження та без виклику моделі під час натискання.
Невідомі сума, постачальник та інші реквізити не блокують подання: власник
отримує окреме повідомлення у відповідь на файл. Працівника про них не питають.
Картки незалежні від поточної чернетки й діалогу; стан та етапи доставки
зберігаються в `_Shuher_Pending` з окремими ключами `invoice:<uid>:<token>`
на 30 днів. Telegram `file_unique_id` визначає стабільний ID документа.
Повторний клік продовжує недоставлені етапи, не створюючи другого запису.

Інші зміни таблиць готуються як конкретна чернетка на 30 хвилин. Користувач бачить
повний попередній перегляд та кнопки **Підтвердити / Скасувати**. Тільки
авторизований Telegram callback автора чернетки може виконати її. Модель не має
інструмента підтвердження. Текстове «так» саме по собі не виконує запис.
Під час підтвердження права перевіряються повторно. Повторний клік не створює
дублікатів. Нова чернетка не замінює попередню без її скасування.

Користувачі працюють із правами `read`, `write_only` або `write` у конкретних
таблицях. Внутрішні `_Shuher_*` недоступні загальним інструментам. Власник
керує доступами в панелі кнопок (`/users` або звичайне прохання). Модель сама
не може надати собі чи іншому користувачу новий доступ. Нові проєкти погоджує
власник. Новий користувач реєструється через Telegram; власник отримує кнопку
налаштування доступу.

Безпосереднє повідомлення працівнику за явним проханням власника надсилається
через `send_staff_message`. Воно не створює облікового доручення. Доручення з
обліком створюється через чернетку `Доручення`; після підтвердження виконавець
отримує сповіщення. Telegram accepted не означає прочитання. Невдалі сповіщення
можна повторити інструментом або запитом `/tasksync`.

## Інструменти

- Актуальні рядки й схема таблиць, зведення заявок/закупівель/блокерів,
  розрахунок залишків, пошук у підключеному архіві, CSV-експорт.
- Заявки з пов'язаною закупівлею, складські рухи, доручення, дозволені статуси.
- Надсилання збережених рахунків власнику, подання нового рахунку, окремі
  операції за групами фото, позначення конкретних рахунків **На оплаті** або
  **Оплачено** після підтвердження. Очікуваний строк зберігається в коментарі.
- Затверджені проєкти, запити на новий проєкт і рішення власника.
- Створення вкладки в поточному робочому файлі (власник).
- Аналіз фото та PDF (також сканів) моделлю, голосові через транскрибування,
  збирання фото накладних у PDF. Кожне вкладення альбому обробляється окремо;
  рахунки отримують власні кнопки проєктів без додаткового текстового запиту.

Підпис **кожного** фото/PDF рахунку для пересилання:

```text
Катана
<фактичний проєкт>
Шакін
```

Реальні постачальник і автор зберігаються в обліку. Фото залишаються фото, PDF —
документами. Порожній статус не є підтвердженням оплати. Передача на оплату не
означає повну оплату. Карткова покупка не погашає окремий рахунок постачальника.

## Межі

Немає імпорту XLS/XLSX, банківських платежів,
автоматичного передання бухгалтерії, створення особистих Google Drive файлів
працівників. Документи читає модель і може помилитися. Невизначені реквізити
перевіряє власник. Подання документа не є оплатою або переданням бухгалтерії.

У Google Sheets немає повних транзакцій між кількома таблицями. Стабільні ID
дозволяють повторити перерваний запис заявки без дубля. Між прийняттям Telegram
повідомлення і збереженням маркера можливий збій; абсолютну exactly-once доставку
Telegram не гарантує. Помилки/частковий успіх не можна представляти як успіх.

## Запуск і перевірка

Конфігурація: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `OPENAI_API_KEY`,
`OPENAI_MODEL=gpt-6.1-sol`, `SPREADSHEET_ID`, `OWNER_IDS`. Не публікувати приватний
`deploy.env.yaml`. Архів задається `HISTORY_SPREADSHEET_ID`.

```sh
cd shuher_simple
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Живі модельні тести запускаються окремо й витрачають API-токени:

```sh
PYTHONPATH=.:tests python tests/live_agent.py --config /private/path/deploy.env.yaml
```

Тест бере лише модель і API-ключ. Sheets і Telegram замінено синтетичними
реєстрами й перехопленням відправлень: бізнес-дані не змінюються, працівники
не отримують тестових повідомлень. Перевіряються багатокрокові діалоги,
конкретні інструменти та їх результати, а не лише текст відповіді.

Cloud Run: `sh deploy.sh` із приватною конфігурацією. Зберігаються черги на
користувача, concurrency=4, max-instances=1, серіалізований доступ до Sheets,
захист Telegram webhook secret та update_id. `/health` має показувати
`model: gpt-6.1-sol`, `architecture: model-first-tools`, `queue: per-user`.
Сам health-check не доводить правильність усіх діалогів.

Логи містять назви інструментів, час і лічильники токенів. Секрети, тексти
розмов, аргументи інструментів і байти фото до журналу не записуються.
