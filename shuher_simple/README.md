# Шухер — Telegram, OpenAI і Google Sheets

**Шухер** — універсальний помічник підприємства. Металообробка, заявки,
закупівлі та склад — перші напрямки; згодом окремими розділами додамо персонал
і керування проєктами. Без Mini App, PostgreSQL чи Cloud SQL.

## GPT-6 Astra і контроль витрат OpenAI

- Основна модель: **GPT-6 Astra** (`OPENAI_MODEL: "gpt-6-astra"`).
  Стандартна ціна: $10 за 1 млн вхідних токенів і $50 за 1 млн
  вихідних; reasoning tokens також враховуються у вихідні.
- Для аналізу та звичайних відповідей застосовується
  `reasoning.effort=medium`; для короткого JSON-маршрутизатора —
  `low`, щоб не витрачати час і гроші на просту класифікацію.
  **Модель максимальна; зусилля не завжди максимальні.**
- Переходимо зі старого Chat Completions на **Responses API**.
  Це підтримує текст, фото (vision), JSON-класифікацію та
  майбутні виклики функцій. Попередні правила підтвердження
  записів у таблиці лишаються без змін.
- У приватних логах Cloud Run кожен запит OpenAI записує лише
  `model`, `input_tokens`, `output_tokens`, `cached_tokens`,
  `reasoning_tokens`. Не записуються текст розмови, фото,
  Telegram ID, API-ключі. Справжні витрати й історію токенів
  дивись на <https://platform.openai.com/usage>.
- Годинний ліміт витрат і білінг налаштовуються в OpenAI Platform,
  не у Google Cloud Run. Cloud Run також має окремий рахунок за
  інфраструктуру. Доступ до моделі залежить від API-організації
  та її лімітів.
- Оновлення вже існуючого Cloud Run (не показуючи секрети):
  `cd ~/MK-Shuher-bot/shuher_simple && git pull --ff-only && sh switch-model.sh && sh activate.sh`.
  Скрипт переписує **тільки** `OPENAI_MODEL` у приватному
  `deploy.env.yaml`, створює резервну копію в домашній теці
  і викликає `deploy.sh`. Під час `activate.sh` введи `ACTIVATE`.
  Перевір `/health`: поле `model` має бути `gpt-6-astra`.
- Якщо в API-організації ще немає доступу до Astra, OpenAI
  поверне помилку; це не означає, що модель автоматично
  заміниться на дешевшу. Перевір API model access та billing
  в OpenAI Platform.

## Керування доступами кнопками — тільки власник

- Новий користувач пише боту `/start`. Власник отримує повідомлення
  **«🔐 Налаштувати доступ»** із кнопкою.
- `/users`, `/access` або фраза «Покажи користувачів» відкриває
  список працівників. Після вибору людини відображається **один список
  усіх бізнес-таблиць**, без готових ролей чи окремого меню режимів.
- Навпроти кожної вкладки є кнопки:
  **Читання** — дозволяє переглядати рядки, експортувати та шукати
  у відповідному історичному розділі, але не записувати;
  **Запис** — можна створювати нові записи й рахунки **без права
  читати/експортувати попередні рядки**; зміна статусу існуючого рядка
  заборонена, бо потребує читання;
  **Ч+З** — і перегляд, і додавання/зміна дозволених статусів.
- Кнопка `✕ Назва` знімає доступ до конкретної таблиці. Галочка `✓`
  позначає поточний режим. Для вкладок «Проєкти», «Запити на проєкти»
  й «Правила Шухера» працівнику можна дати тільки читання.
- **Кнопки доступу застосовуються одразу.** Натискаєш
  «Читання», «Запис», «Ч+З» або ✕ — відповідний дозвіл змінюється
  без другого екрана підтвердження. Це стосується **тільки доступів**:
  записи закупівель, складські операції, рахунки та створення
  проєктів і далі вимагають підтвердження.
- Для прискорення панель одним запитом читає Telegram-користувача
  та його права, а змінює лише потрібний рядок, не переписуючи
  всі доступи. Після зміни одразу оновлюється поточне меню.
- Старі записи `write` в `_Shuher_Access` зберігають попереднє
  значення **читання + запис**, їх не треба мігрувати. Лише нове
  `write_only` означає «Запис» без перегляду.
- Права зберігаються в прихованій вкладці `_Shuher_Access`,
  а всі дії доступні лише власнику за Telegram ID. Старі повідомлення
  з кнопками наборів ролей не застосовують старі шаблони:
  відкрий `/users` для актуальної панелі.
- Для розгортання коду на Cloud Run:
  `git pull --ff-only && sh deploy.sh && sh activate.sh`.
  Активація реєструє `callback_query` разом із `message`.
  Команди `/grant`, `/revoke` лишилися як резервні.

## Доручення власника: особисті повідомлення в Telegram

Шухер має **виконувати** прямі доручення власника, а не пропонувати
чернетку й перепитувати без необхідності. Наприклад:

- «Напиши Юрі та Сергію, що можуть починати працювати» — **два окремі**
  повідомлення через Telegram Bot API.
- «Фото отримав, номер ТТН прочитав, Юрі напишеш?» — визначити Юрія
  тільки серед зареєстрованих користувачів, узяти доречний текст із
  останньої розмови або, за наявності свіжого фото, прочитати його
  перед відправленням. Не повторювати старе повідомлення іншої теми.
- «Можеш Юрі надіслати ТТН?» — короткий контекстний запит, а не прохання
  пояснити, як самому надіслати.

Надсилання працює **лише за явним дорученням власника** і лише на
Telegram ID людей, які вже написали боту `/start`. Сервер перевіряє
одержувача, а не довіряє вигаданому GPT-адресату. Якщо з розмови
неможливо встановити зміст повідомлення, Шухер попросить уточнити.
Переказ із фото не гарантує правильності нерозбірливого номера ТТН —
у разі сумніву потрібне уточнення.

**Надсилання не потребує додаткового «так».** Telegram API повертає
успіх/помилку для кожного одержувача; це не означає, що людина прочитала
повідомлення. Власник отримує окремий звіт щодо кожного адресата.
Доручення не виконуються повторно під час деплою. Операції з
Google Sheets залишаються з підтвердженням.

## Робоча поведінка

- Звичайний текст обробляється як розмова з GPT, без необхідності писати
  слеш-команди. Підтримуються фото, голосові до 2 хвилин і коротка
  персональна пам'ять. `/new` очищає діалог.
- Працівник із правом на Заявки надсилає потребу. Для заявки
  **обов'язкові погоджений проєкт, найменування, кількість і одиниця
  виміру**. Власник не погоджує звичайні заявки. Після текстового
  «так» створюється пов'язаний рядок Закупка.
- Користувачі з правом запису (`write` або `write_only`) у «Закупка» отримують Telegram-сповіщення
  про нову заявку. Для нового товару чи постачальника, який треба
  шукати, власник отримує окремий сигнал.
- Проєкти: ВК-1000, STF, ПА-31, ДП, Купянськ/Бахмут, Лягушка, МЗВ,
  Офіс (хіміків), Офіс (медведь), Мет обробка. Останній —
  загальновиробничі витрати, але НЕ автоматичне значення замість
  невідомого проєкту.
- Якщо проєкт не вказали, бот показує список на вибір. Якщо проєкту
  немає — окремий запит. **Тільки власник** може додати його в
  довідник після `/projectapprove ID` і підтвердження. Нові
  проєкти неможливо створити через звичайну `/add`.
- Рахунок або скрин оплати: окремий розділ Рахунки. Потрібен
  підтверджений проєкт перед оформленням; без нього неможливо
  записати рахунок. Після підтвердження власникові надсилаються
  опис, фото або оригінальний PDF. Бухгалтерії без рішення власника
  бот нічого не відправляє. **PDF рахунку наразі НЕ розпізнається
  автоматично**: файл передається для ручної перевірки.
- Фото видаткових накладних можна зібрати до 6 штук в один PDF:
  «Збери PDF накладних, проєкт STF» або `/receiptpdf STF`.
  Це **не фіксує прихід на склад** — приход оформляється окремою
  підтвердженою складською операцією.
- Історичні дані: «Які труби раніше замовляли на STF-02?» або
  `/history STF-02 труба`. Наводити джерело й не підміняти старою
  інформацією поточний статус.
- Інші функції: `/today` — нові закупівлі за день (власнику),
  `/balance` — поточні залишки (за правом), `/status` — зміна
  дозволеного статусу, `/export` — CSV. Будь-яка зміна таблиць
  вимагає окремого **текстового** «так».

## Платежі та бухгалтерія

Правила власника в «Правила Шухера»: звичайні рахунки оплачуються
у **середу та п'ятницю**, якщо власник передав рахунок до бухгалтерії
до **17:00 попереднього дня**. Термінові рахунки — позачергово.
Це правило, а **не автоматичне виконання платежів**. Власник сам
перевіряє та передає рахунки до бухгалтерії.

## Безпечне переключення на нову таблицю

Код відрізняється від поточної Cloud Run-версії до завершення розгортання.
У Cloud Shell, де раніше розгортався бот:

```sh
cd ~/MK-Shuher-bot/shuher_simple
git pull --ff-only
sh switch-data.sh
```

`switch-data.sh` без розкриття секретів зберігає приватний
`deploy.env.yaml`, створює резерв у домашній теці, замінює
`SPREADSHEET_ID`, додає `HISTORY_SPREADSHEET_ID` і викликає
`sh deploy.sh`. Перевір у Telegram `/tables`, `/projects`,
`/history STF труба` та чернетку рахунку без проєкту.

**Не видаляй стару робочу таблицю, доки Cloud Run не підключився
до нової й перевірки не пройшли.** Стара тестова таблиця вже
видалена як непотрібна.

## Що ще НЕ реалізовано

- Повноцінний OCR PDF рахунків, імпорт проєктних відомостей із XLS/XLSX
  та PDF, автоматичне звіряння комплектності STF і точних залишків
  за складськими місцями.
- Автоматичний вечірній бухгалтерський XLSX за видатковими та
  безпомилкова OCR-звірка накладних; наразі можна зібрати фото в PDF.
- Пряме виконання оплати або пересилання в бухгалтерський Telegram-чат:
  рішення й передача залишаються за власником.
- Автоматичне виявлення всіх шахрайських чи помилкових рахунків.
  ШІ може підсвітити сумнівні дані, але не заміняє перевірку власника.
- Транзакційні гарантії сильно паралельної роботи та складське
  резервування за проєктами.

`/health` підтверджує запуск Cloud Run, але справність ланцюжка
заявка → закупівля → рахунок → склад потрібно перевірити в Telegram
перед додаванням персоналу.
